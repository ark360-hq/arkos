## [Unreleased]

### Security

- **MCP tool calls fail closed when they cannot be audited** (SPEC-0205, ADR-0048). The gateway writes an `accepted` audit row for the configured site before invoking the downstream API, then a `success` or `failure` outcome row. A missing `Gateway:SiteId`, a failed audit HTTP post, or a throwing security audit sink refuses the tool instead of swallowing the error. `/api/internal/gateway-audit` persists through `ISecurityAuditLog` and returns JSON on success so the write is not lost on an empty 202 body.

### Added There was no observability at all — no tracing, no metrics, no alerting — while `src/README.md` advertised "Shared OpenTelemetry and health defaults (Aspire-ready)" and the container templates set `OTEL_*` variables for an exporter that was not installed. `BTROS.ServiceDefaults` was 40 lines of health checks. It now configures OpenTelemetry tracing and metrics across api, web, gateway **and** the worker, exporting to Application Insights when a connection string is present and degrading to silence when it is not, so local development and the test suite need no Azure resource. Outbound HTTP is instrumented deliberately: BioStar, Stripe and ACS are where the swallowed failures live, and tracing them is what makes a retry storm legible as one picture. The counters matter more than the traces: **the audit's recurring finding was not that things break, but that when they break nobody is told.** Five now record — a failed credential revocation, background work that has gone terminal and will not be retried, undelivered messages, undelivered push, and audit writes that failed while the originating action proceeded (the ADR-0040 trade-off, only defensible if someone can see how often it fires). They live in `BTROS.Domain` rather than ServiceDefaults, because the code that knows a failure happened is in Infrastructure and `System.Diagnostics.Metrics` is in the base class library, so Domain stays dependency-free. Two things worth recording: the vulnerable-dependency gate **correctly refused** the first package set (`OpenTelemetry.Api 1.13.1`, GHSA-g94r-2vxg-569j) and the versions are pinned past it rather than allow-listed — suppressing a real security gate on the spec meant to make failures visible would have been the wrong trade; and `Azure.Identity` stays pinned at 1.13.1 per ADR-0033, so the Azure Monitor package is held at 1.3.0 to avoid a transitive `Azure.Core` bump that collides on `DefaultAzureCredential`. **Not included: the Application Insights resource, the action group and the alert rules** — those need an alert destination, which is a decision rather than code.
- **A paying customer can be given their own environment without a repository change** (SPEC-0199, ADR-0043 unchanged; SPEC-0200 written). The PRD is explicit that *"a deployment is one customer's portfolio"* and that multi-tenant SaaS across unrelated customers is a non-goal — so every customer gets their own environment, provisioned **at signing**, when a paying customer is waiting. Two things made that impossible. **First, all four secrets were repository-level and shared**: provisioning a second customer would have given both instances the same `INTERNAL_SERVICE_KEY` — one key minting **Admin on every customer instance** — and one `FIELD_ENCRYPTION_KEY` protecting every customer's BioStar credentials, reintroducing precisely the cross-tenant exposure the per-customer model exists to remove. Secrets now resolve per environment, from **that environment's own Key Vault first**, falling back to a repository secret (which is what migrates ARK360's existing values and preserves its live encryption key) and only generating for a genuinely new environment. Resolved values are written back after provisioning, **set-if-absent**, and a value that differs from what the deploy resolved **fails the run rather than overwriting** — silent rotation of the encryption key is data loss wearing a green tick. **Second, there was no way to create the first operator**: a fresh environment has an empty user store, self-registration is refused outside demo environments (SPEC-0180), and "have an existing admin promote you" is circular, so a correctly configured customer environment was one nobody could log into — which also blocked converting ARK360's own environment out of demo mode. A first-admin bootstrap now creates an `Admin` from configuration, audited, and runs **only when the user store is empty** — including suspended and archived accounts — so it cannot take over a running instance whatever it is pointed at, and it is inert the moment it succeeds. This supersedes SPEC-0184's rule that the deploy must never generate `FIELD_ENCRYPTION_KEY`: a new customer environment must be able to self-generate or adding a customer would need a manual secret, and the invariant that matters — a key in use is never replaced — is now enforced harder rather than weakened. Recorded in the spec rather than flipped silently.

### Fixed

- **Retracted: the BioStar credentials were never committed to git.** The pilot-readiness audit recorded a live-looking BioStar API key and admin password as committed at `appsettings.Development.json:6-9`, rated it Critical, and told the reader to rotate immediately. **That was wrong.** The file is gitignored (`.gitignore:35`) and has never been committed — `git log --all --full-history` on the path is empty and `git log -S` on the key string finds nothing anywhere in history. ### Added

- **Building master credentials are encrypted at rest** (SPEC-0184, ADR-0043). `SiteConfig.BioStarAdminPassword` and `sites.WebhookSecret` were stored as plaintext, so a read of one database column yielded administrative control of a building's access-control system — a threat Azure's platform disk encryption does not touch, because it is about a backup copy, a support query, or a compromised read-only account rather than a stolen disk. **The obvious tool was the wrong one:** there is no Data Protection configuration anywhere in the solution, so its keys are ephemeral, and encrypting a column with them would have made every stored credential permanently unreadable on the next redeploy — worse than the plaintext it replaced. ADR-0043 instead uses AES-256-GCM over a dedicated Key Vault–sourced key: a versioned `v1:` envelope of `nonce ‖ tag ‖ ciphertext` with a fresh 96-bit nonce per value, so the same password stored twice does not look the same and a tampered value fails rather than decrypting to rubbish. **Migration is lazy, not a data migration** — an unprefixed value is read as plaintext and encrypted on its next write, so there is no downtime and no window where a half-migrated table is unreadable. Outside Development and Testing the key is **mandatory**: startup fails without it, because encryption that silently degrades to plaintext would be invisible until someone read the table. The deploy seeds it from a `FIELD_ENCRYPTION_KEY` secret and **refuses to generate one** — unlike the gateway key, where a random value merely locks the gateway, a fresh field key each deploy would orphan every previously encrypted credential. Two things surfaced while building it: a tamper test that mutated base64 text was **flaky**, sometimes producing `FormatException` rather than a failed decrypt, so it now mutates decoded bytes and `Unprotect` raises one exception type for any unusable value; and the absence of Data Protection also means **antiforgery tokens are protected with ephemeral keys**, invalidating on every restart and unable to validate across replicas if `web` ever scales past one — a real latent defect, out of scope here, recorded in ADR-0043 for its own spec.

### Added

- **An operator can see that a door credential has not actually been taken away** (SPEC-0183 REQ-005/006, completing the spec). The durable retry landed first: a failed BioStar revocation is queued in the same transaction as the archive and retried with backoff. But until now the console showed a resident as cleanly **moved out** while their credential was still live — the same wrong belief the empty `catch` created, arrived at by a different route. The residents list now carries a badge for any resident whose revocation has not completed: **"Revoking key"** while it is still being attempted, and **"Key not revoked"** in red once the attempt cap is reached, with a tooltip saying the credential may still open doors and the access system needs checking. A new `GET /api/residential/residents/revocations/outstanding` reports them for the current site, scoped like every other operator read. The revocation payload gains a `ResidentId` used **only** for this correlation — it is not needed to perform the revocation, and it is documented as such so a later reader does not mistake it for load-bearing; on the erase path the resident is gone by then, which is correct, because there is nothing left to badge. The badge fetch is best-effort at the call site: a residents list that loses its badges is better than one that fails to load, and the retry keeps running regardless of whether the console can see it. One test initially asserted against the wrong `catch` block — the page has several, and scoping to the first occurrence in the file tested an unrelated access-levels fetch; the assertion is now bounded to the method it is about.

### Fixed

- **A failed door-credential revocation is no longer lost** (SPEC-0183). This is the one finding in the pilot-readiness audit capable of causing physical harm rather than commercial embarrassment. `ResidentService.MoveOutAsync` and `EraseAsync` wrapped the BioStar revoke in an **empty `catch`**: when BioStar was unreachable — a network blip, an expired admin credential, a duplicate-login collision, a vendor outage — the platform archived the resident, recorded them as moved out, and their phone kept opening the building. No retry, no dead-letter, no alert, no reconciliation, and on the erase path the local `BioStarUserId` was then destroyed, so there was not even enough information left to retry by hand. The revocation is now queued as an outbox item **in the same transaction as the archive** (SPEC-0186), so the two cannot diverge: either the resident is moved out and the revocation is guaranteed to be attempted, or neither happened. The erase path queues **before** the purge and the payload carries the BioStar identity itself — a deliberate, minimal retention past an erasure request, kept only until the credential is provably gone, because the alternative is an erased resident whose key still works. BioStar being unreachable retries with capped backoff; an unreadable payload fails immediately rather than hiding behind a queue that looks busy; a successful revocation writes an audit row recording how many attempts it took. `IUnitOfWork` gains an explicit `SaveChangesAsync`, because the enqueue deliberately does not save itself — that is what lets it join the caller's transaction — and the erase path has no repository write to flush it. **The durable part is a banned-pattern rule**: an empty `catch` in application source now fails the build, with a comment inside the block enough to satisfy it, since swallowing is sometimes right but has to be a decision with a reason written next to it. The rule uses `perl` rather than `grep -P`, because BSD grep on macOS has no PCRE and a `-P` rule passes silently for every developer on a Mac and only bites in CI — which is exactly how the repository's existing bare-TODO check behaves today. Verified by seeding the violation and watching it fail, then removing it.

### Added

- **The platform has a background-job tier** (SPEC-0186, ADR-0042). `BTROS.Functions` was a reserved placeholder whose `.csproj` was a single self-closing line — no SDK, no triggers, no host — and the only background work in the product was an in-process poller in the API that defaults to disabled. Everything queued behind that absence is real: a failed BioStar credential revocation has nowhere to retry from (SPEC-0183, where a moved-out resident's key keeps working), visitor passes never expire, rent charges are never generated from a tenancy's cadence, and notification failures never retry. **ADR-0042 rejects the Azure Functions the placeholder's name presumed**: the platform is already Container Apps provisioned by Aspire and `azd`, the primary workload is a drain loop rather than an event burst, and Functions would add a Function App, a storage account and a second deployment path to buy managed retry the outbox has to own anyway — the attempt count and terminal state are part of the operational record. The project is renamed **`BTROS.Worker`**, because a name asserting a hosting model the platform does not use is the same confusion the stale `Sentinel*` config keys caused. Durable work is an **outbox table written in the same transaction as the state change that caused it** — that co-transaction is the entire point, and it is why a broker was rejected for now: a broker reintroduces the dual write the outbox exists to remove. The claim is a single conditional `ExecuteUpdate` whose affected-row count decides ownership, never a read-then-write, so two workers racing an item cannot both win; integer set-clauses only, matching the atomic capacity claim already used for amenity bookings. Failures retry with capped exponential backoff until an attempt cap makes them terminal, a handler that throws is recorded rather than fatal, an unroutable kind fails immediately rather than hiding behind "pending", and `CountStalledAsync` is the signal an operator alert will hang off once SPEC-0187 lands. Thirteen tests cover it, including two drainers over one queue processing each item exactly once. `BTROS.Domain` stayed dependency-free — the drainer logs, so the build's layering rule pushed it into Infrastructure, which is where it belongs.

- **Payment + identity webhooks are exactly-once and transition-safe, unmapped events stop looking like bad signatures, and refunds are an atomic claim** (SPEC-0166, no migration): the whole-codebase review found four money-touching correctness gaps in the Stripe payment + Stripe Identity webhook paths and the operator refund. **(1) Not exactly-once** — both `HandleWebhookAsync` handlers marked the event processed (one `SaveChanges`) and then applied the state mutation (a **second** `SaveChanges`), two separate commits; a crash between them persisted the idempotency marker but lost the mutation, so the replay was swallowed as a duplicate and the payment stayed `pending` (lost settlement) / the verification unresolved. In the container this was already handled — Aspire sets `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` on the web app, so ASP.NET restored the HTTPS scheme and HSTS was already emitting (verified live: the prod site returns `strict-transport-security: max-age=2592000`). The gap was that this stayed implicit/platform-dependent: a host that doesn't set that env var sees the request as non-SSL, and a hard `Secure`/`Always` antiforgery policy then 500s every render (`AntiforgeryOptions.Cookie.SecurePolicy = Always, but the current request is not an SSL request` — reproduced in the non-container `Testing` environment). The Web host now registers `UseForwardedHeaders` (`X-Forwarded-Proto`/`-For`, trusting the ingress; `X-Forwarded-Host` deliberately **not** honoured so host filtering still sees the real `Host`) explicitly in code, and uses `CookieSecurePolicy.SameAsRequest` (Secure once the scheme is HTTPS, never throwing on a plain-HTTP request) — so scheme-dependent logic (HSTS / HTTPS-redirect / Secure cookies) is correct on every host, container or not, independent of the platform env var. Defence-in-depth only — no auth/authorization, routing, or rendering change (that hardening is SPEC-0095). Verified in the web preview (Home + `/login` render under the CSP, no console violations, Blazor circuit live, all five headers present) and reproduced/fixed the non-container render-500 by running the host in the `Testing` environment. Guarded by `SecurityHeadersTests` (middleware sets all headers + CSP directives; a real `/` response carries them; a forged Host → 400 while localhost → 200; all three appsettings restrict `AllowedHosts`; antiforgery cookie flags; `X-Forwarded-Proto: https` renders + emits HSTS).
